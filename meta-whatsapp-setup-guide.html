WhatsApp Restaurant AI Host — Meta / WhatsApp Setup Guide

What to set up in Meta before you deploy, and how each value flows into the AWS deployment. Two phases, because the webhook URL only exists after deploy.

You set up the WhatsApp side once, in the Meta consoles. Some of the values you collect are secrets and some are plain configuration. They take different paths into the AWS deployment, and getting that split right matters for security.

Phase A — Set up WhatsApp and collect what you need before deploy

All of this happens in the Meta consoles. None of it touches AWS yet.

A.1  Create the app and get a sandbox test number

  1. Create a Meta Developer App (type: Business)At developers.facebook.com → My Apps → Create App → choose the Business type. If you have no Business Portfolio yet, Meta auto-creates a default one and links the app to it — you do not need to create or verify a business to test.
  2. Add the WhatsApp product to the appIn the app dashboard, click Add Product and add WhatsApp. This automatically provisions a WhatsApp Business Account (WABA) and a free test number you can use immediately — no business verification, no number registration.
  3. Add your phone as a test recipientIn WhatsApp → API Setup, under To, add and verify your own WhatsApp number as an allowed recipient. In test mode the sandbox number can message up to 5 verified recipients — enough to exercise text, voice notes, and calls end to end.
ⓘ
The sandbox test number is the one number behind all three channels for the demo — the recipient taps it to message and to call (text, voice notes, calls). When you later move to a real business number, see Going to production.

A.2  Collect the values the deployment needs

  1. Copy the Phone Number ID and WABA IDconfig In WhatsApp → API Setup, copy the Phone Number ID (a numeric id, not the phone number itself) and the WhatsApp Business Account ID. These are identifiers, not secrets.
  2. Copy the App ID and App Secretconfig App ID  ·  secret App Secret. Both live in App Settings → Basic. The App Secret is the HMAC key Meta uses to sign every webhook (X-Hub-Signature-256); the deployed Lambda recomputes that signature to prove a request really came from Meta. Treat it like a password.
  3. Get an Access Tokensecret Quick test: the temporary token shown in WhatsApp → API Setup works immediately, but expires in ~24 hours — fine to validate the flow, just re-run the secret-populate step when it lapses. Recommended even for the sample: in Business Settings → Users → System Users, create a system user, assign it to your app and WABA, then Generate Token with scopes whatsapp_business_messaging and whatsapp_business_management for a long-lived token. (System Users use the auto-created portfolio but do not require business verification.)
  4. Choose your own Verify Tokensecret This one you invent — any hard-to-guess string (e.g. openssl rand -hex 24). Meta echoes it back during the one-time webhook handshake so your endpoint can confirm the subscription. You will type the same value into the Meta webhook config in Phase B.

Where each value goes

This is the contract between “what you copied from Meta” and “how the architecture gets configured.” The secret/config split is the part to get right.

🔑
Why secrets are not CDK parameters. Anything passed as a CDK parameter or context value ends up baked into the synthesized CloudFormation template and, often, into source control. For tokens and signing keys that is a leak. So CDK only creates empty Secrets Manager containers and grants the Lambda scoped read access; you populate the values out-of-band after the secret exists. The non-secret identifiers are fine to pass as parameters.
ⓘ
So can deploy-all.sh create and populate the secret for me? Yes — and that is the recommended flow. CDK makes the empty container; then deploy-all.sh runs aws secretsmanager put-secret-value to inject the value. Two rules keep it safe: (1) pass the value as an environment variable, not a --flag — a flag value leaks into shell history and ps output, an env var does not; (2) keep it idempotent — if the env var is set, put the value; if it is empty, skip and assume the secret was populated by hand, so re-running deploy never wipes a secret you set manually. This is exactly the empty-container-then-put pattern below; the only thing to avoid is turning the value into a CfnParameter.

The deploy step in between

Populate the three secrets, pass the config, and read the webhook URL back out.

The intended shape once the webhook stack exists. The secret values are passed by environment variable so they never land in shell history flags or the CloudFormation template:

# 1. Provide the three Meta secrets as env vars (not as CLI flags).
#    Env vars stay out of shell history and `ps` output; a --flag would not.
export WHATSAPP_ACCESS_TOKEN="EAAG...your-system-user-token"
export WHATSAPP_APP_SECRET="your-app-secret"
export WHATSAPP_VERIFY_TOKEN="the-string-you-invented"

# 2. Deploy. Non-secret identifiers ride as flags; the script puts the
#    secret values into the Secrets Manager containers CDK created.
./scripts/deploy-all.sh \
  --deploymentPrefix qsr-wa \
  --phone-number-id XXXXXXXXXXXXXXX \
  --waba-id XXXXXXXXXXXXXXX \
  --app-id XXXXXXXXXX

# 3. Read the webhook URL out of the deploy outputs.
cat cdk-outputs/wa-webhook.json   # -> WebhookUrl: https://abc123.execute-api.us-east-1.amazonaws.com/prod/webhook

Inside the script, the populate step is an idempotent CLI call per secret — put the value only when the env var is set, otherwise leave a hand-populated secret untouched:

# pseudo-excerpt of what deploy-all.sh runs after CDK creates the empty secret
if [ -n "$WHATSAPP_ACCESS_TOKEN" ]; then
  aws secretsmanager put-secret-value \
    --secret-id "qsr-wa-whatsapp-access-token" \
    --secret-string "$WHATSAPP_ACCESS_TOKEN"
fi
# ...same guard for app-secret and verify-token. Empty env var = skip = no wipe.
ⓘ
The webhook URL is served on the AWS-managed execute-api DNS name with an AWS-managed certificate — no custom domain, no certificate for you to provision. That certificate-free posture is the whole reason this variant uses WebRTC + an API Gateway webhook instead of SIP. Anyone can deploy it without owning a domain.

Phase B — Finish wiring in Meta after deploy

Now that the webhook URL exists, go back to the Meta app and connect it.

  1. Configure the webhook callback URLIn the app dashboard → WhatsApp → Configuration → Webhook, click Edit. Paste the Callback URL from cdk-outputs/wa-webhook.json and the Verify Token — the exact same string you put in Secrets Manager.
  2. Let Meta complete the verification handshakeOn save, Meta sends a GET with hub.mode=subscribe, hub.verify_token, and hub.challenge. The Lambda checks the token against the secret and echoes the challenge. A green check means the subscription is live.
  3. Subscribe to the webhook fieldsSubscribe the WABA to messages (text, image, document, audio/voice notes) and calls (the Calling API event carrying the SDP offer). Without these subscriptions, Meta will not POST events to your endpoint.
  4. Enable the Calling API on the numberIn WhatsApp → Calling (or via call settings), enable calling for your phone number so the Call channel works. The default configuration is Graph APIs + Webhooks for signaling with WebRTC for media — exactly what this architecture expects.
  5. Send a test message and place a test callFrom the WhatsApp number you added as a test recipient, message the sandbox number, send a voice note, and tap Call. Confirm the webhook fires and the agent responds on all three channels. That is a complete working demo — no business verification needed.

Going to production later, real business only

None of this is needed to test. Do it only when you are taking the sample to a real restaurant on a real number and messaging real customers.

  1. Create / confirm a Business PortfolioAt business.facebook.com, set up the Business Portfolio that owns the app, WABA, and number (the test path used an auto-created one).
  2. Complete business verificationIn Business Settings → Security Center, finish verification. Required to message customers beyond your test recipients and to raise messaging limits. It can take days — start early.
  3. Register a real production phone number + display nameIn WhatsApp → API Setup / Phone Numbers, add the real number (must receive the verification code and not already be on the consumer WhatsApp / WhatsApp Business app). Complete code verification and set the business display name (subject to Meta name-review). Re-collect the new Phone Number ID and re-run the config/deploy with it.
  4. Submit for App Review and switch to LiveComplete App Review for whatsapp_business_messaging + whatsapp_business_management, then switch the app from Development to Live mode so it can message the general public.
  5. Approve Utility message templatesFor proactive order confirmations sent outside the 24-hour window, get your Utility templates approved in the WhatsApp Manager.
